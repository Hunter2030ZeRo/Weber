# Weber 제품 합격 기준

2026-09-09 사용자 요구를 기준으로 한다. 이 문서는 목표와 검증 계획이며,
아래 기능의 구현 완료를 의미하지 않는다. 현재 구현 상태는 README의 검증 기록을 따른다.

## 필수 목표

| 목표 | 합격에 필요한 증거 |
| --- | --- |
| Electron 앱 최소 수정 이식 | 버전을 고정한 실제 Electron 앱과 VS Code 소스 빌드의 이식 패치 및 기능 회귀 결과 |
| 낮은 메모리와 높은 성능 — 최우선 | 동일 기능·보안 조건에서 Electron과 비교한 전체 프로세스 메모리, 시작 시간, 입력 지연, 프레임 시간, CPU 측정 |
| 운영체제 통합 | 메뉴·트레이·클립보드·드래그 앤 드롭과 설치 패키지의 Windows/macOS/Linux 실제 검증 |
| 다중 창 | 독립 창의 생성·포커스·종료·재생성, 창 간 통신, 고장 격리, 반복 사용 후 자원 회수 검증 |
| 프로세스 격리와 보안 | 렌더러 프로세스 격리, 권한 경계, 격리된 preload 실행 환경, 운영체제 샌드박스 및 부정 테스트 |

성능 최적화를 이유로 필수 기능이나 격리 수준을 낮춘 결과는 합격으로 인정하지 않는다.
Chromium 제거 또는 Rust 사용 자체는 성능 향상의 증거가 아니다.

## 호환성 계약

Electron에서 가져온 소스와 이력을 보존하는 실제 포크 작업은 여전히 필요하다.
현재 Electron 참조 서브모듈과 독립 Rust 호스트를 완성된 포크로 부르지 않는다.

기존 앱 이식은 Node 백엔드를 우선 기준으로 삼는다. Electron 모듈 로딩,
공개 API의 반환 방식·이벤트 순서·오류 동작, preload/contextBridge/ipcRenderer,
BrowserWindow/webContents 등 실제 사용 계약을 조사하고 호환 시험으로 고정한다.
현재 비동기 창 API와 window.weber.invoke 예제는 그 계약을 충족했다는 증거가 아니다.
지원하지 않는 기능을 성공한 것처럼 처리하는 빈 구현은 허용하지 않는다.

최소 수정의 목표는 런타임 의존성, 실행·빌드·패키징 설정 변경이다.
앱의 화면이나 핵심 로직을 재작성해야 한다면 해당 이식은 목표 미달이다.
각 앱의 수정 파일·라인·이유를 기록하며, 허용 변경의 정량 한계는 실제 조사 후 정한다.

VS Code는 이름만 있는 예제가 아닌 최종 대표 검증 대상이다. 첫 조사에서 정확한 소스
커밋과 해당 Electron 버전을 고정한다. 편집·저장·검색·다중 창·터미널·확장 호스트·
웹뷰·한글 입력·접근성을 검증 항목에 포함한다. 각 항목의 Electron API, 웹 표준,
운영체제 기능 의존성을 소스에서 확인한다. API 이름만 맞추어 통과시키지 않는다.
Obscura의 DOM/CSS/입력/웹 API 호환성 부족도 프레임워크의 차단 문제로 관리한다.

TOML의 node/bun/native 실행 시점 선택은 유지한다. Bun의 호환 범위는 별도로 검증한다.
Rust native는 같은 프런트엔드와 통신 계약을 사용할 수 있어야 하지만, JavaScript
백엔드를 Rust로 자동 번역하는 기능은 아니다. 기존 Electron 앱의 무수정 Native
실행을 약속하지 않는다.

## 구조 원칙

- 운영체제 창·메뉴·권한 중개를 담당하는 호스트와 Obscura 렌더러를 분리한다.
- Node/Bun/Rust 백엔드 선택과 렌더러 격리는 독립된 설계 축으로 둔다.
  현재 Rust 콜백의 GUI 스레드 내 실행 구조도 이 원칙에 따라 재설계한다.
- 초기 격리 기준은 창별 렌더러 프로세스다. 공유 최적화는 신뢰 경계와 고장 격리를
  유지한다는 검증 후에만 도입한다. V8 isolate만으로 프로세스 격리를 대체하지 않는다.
- preload는 페이지와 분리된 실행 환경에서 동작해야 한다. 파일·네트워크·클립보드·
  프로세스 실행 권한은 호스트에서 검증한다. IPC 발신 창/문서/출처, 수명, 메시지 크기,
  스키마와 허용 기능을 확인하고 탐색·종료 시 권한을 회수한다.
- 운영체제별 샌드박스와 자식 프로세스 핸들 상속 정책을 명시한다. 프로세스 분리만
  완료한 상태를 샌드박스 완료로 표시하지 않는다.
- PNG 파일 인코딩/디코딩 경로를 제거하고 원시 프레임 전송과 변경 영역 갱신을
  도입한다. 공유 메모리를 쓴다면 크기·소유권·동기화·수명을 검증한다.
- GUI 이벤트 루프에서 탐색과 JavaScript 실행을 분리한다. 무변경 화면에서는
  불필요한 렌더링을 줄이고, 숨겨진 창의 정책을 명시한다.

## 성능 검증 계약

현재 Electron 대비 측정 결과는 없다. 임의의 절감률을 달성 수치로 발표하지 않는다.

비교 대상 앱/런타임/엔진 커밋, 릴리스 빌드 옵션, 운영체제, 하드웨어, 화면 크기·DPI,
데이터·확장 구성과 보안 설정을 고정한다. 콜드/웜 시작을 구분하고 순서를 교차하여
반복 실행한다. 원자료, 중앙값, p95, 표본 수와 변동성을 공개한다.

| 시나리오 | 측정 |
| --- | --- |
| 빈 창, 실제 편집기, 창 1/5/10개 | 전체 프로세스 트리의 메모리와 유휴 CPU |
| 시작 및 프로젝트 열기 | 프로세스 시작부터 첫 표시와 실제 입력 가능 시점까지 |
| 입력·스크롤·창 크기 변경 | 입력부터 표시까지 지연, 프레임 시간 p95, 누락 프레임 |
| 큰 파일·검색·백엔드 작업 | 완료 시간, CPU, 최대 메모리 |
| 창 열기/닫기 반복 및 장시간 유휴 | 자원 누수와 안정 상태 복귀 |

Linux에서는 PSS와 private 메모리를 함께 기록하고 RSS 합계의 공유 페이지 중복을
명시한다. 다른 운영체제의 메모리 지표는 정의를 기록하며 서로 동일한 값으로
간주하지 않는다. 호스트·렌더러·백엔드·보조 프로세스를 모두 포함한다.

대표 작업에서 메모리 감소와 성능 향상이 측정 오차를 넘어 반복 재현되어야 한다.
핵심 작업의 유의미한 퇴행은 해결하거나 합격 미달로 기록한다. 구체적인 수치 예산은
첫 기준선 측정 뒤 설정한다. 기능을 생략한 빈 창 결과로 VS Code 성능을 주장하지 않는다.

## 구현 순서와 완료 조건

1. Electron/VS Code 소스 버전 고정, 사용 API·웹 기능 조사, 이식 패치 예산과 성능
   기준선 도구 작성. 실제 Electron 포크 및 라이선스 고지 보존 경로 확정.
2. 원시 프레임 엔진 경계, 렌더러 프로세스 분리, 다중 창 라우팅과 수명 관리 구현.
   렌더러 하나의 종료·무한 실행이 다른 창과 호스트를 멈추지 않는지 검증.
3. 격리된 preload와 권한 중개, 운영체제 샌드박스 구현. 다른 창 접근, 오래된 IPC,
   무권한 파일 접근, 비정상 메시지와 렌더러 충돌에 대한 부정 테스트 통과.
4. Electron 호환 API와 웹 호환성을 실제 앱에서 단계적으로 검증. 메뉴, 트레이,
   클립보드, 드래그 앤 드롭, 완전한 입력/IME/접근성과 다중 모니터 동작 구현.
5. Windows/macOS/Linux 설치·실행·업그레이드·제거 검증, 필요한 서명/공증 경로 마련.
   VS Code 기능 및 동일 조건 성능 비교를 통과한 범위만 지원 대상으로 발표.

성능과 보안 검증은 마지막 단계에만 수행하지 않고 각 구조 변경의 승인 조건으로 둔다.
