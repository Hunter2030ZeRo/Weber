# AOT 시작 시간·메모리 원인 분석 — 2026-10-19

아래는 원래 standalone 릴리스의 분석 기록이다. 후속 바인딩 구현과 현재 측정은 [프레임워크 검증](framework-validation.md)에 별도로 기록했다.

현재 AOT 경로는 Servo/SpiderMonkey에 Hermes와 미러 DOM을 추가한다. 브라우저 기본 기능을 다시 구현하는 JS 호환 라이브러리의 초기화와 추가 런타임 비용이 크다. 네이티브 AOT 컴파일이 적용된 상태에서도 이 초기화는 실행 시점에 일어난다.

애플리케이션 코드는 수정하지 않았다. 기존 release 실행 파일·패키지·검증 보고서를 보존하고, 별도 진단 실행 파일을 실제로 컴파일하여 실행했다.

## 비교 범위

- 기존 release 중앙값: AOT 시작 232.35ms / PSS 162.17MiB, web 시작 191.31ms / PSS 132.88MiB.
- 시작 지표는 Rust main 진입부터 앱 준비 이후 첫 고유 네이티브 버퍼 제시까지다. ELF 로더 시간은 제외하며, 파일 캐시가 따뜻한 측정이다. OS 실행 요청부터의 콜드 스타트 전체를 뜻하지 않는다.
- web은 Servo DOM과 SpiderMonkey에서 같은 TSX를 실행한다. Hermes 라이브러리가 링크되어 있으나 Hermes 런타임은 초기화하지 않는다.
- AOT는 동일한 Servo DOM/SpiderMonkey를 유지하면서 별도의 Hermes 힙, 미러 DOM, 동기 브리지를 사용한다. 엔진 한 개를 다른 엔진 한 개로 교체한 실험이 아니다.
- Servo `aac43a3f31a259f04a574f5ec4e959c943ad7cc7`, Hermes `17b37301da5da4a2cd55d78f9697c46c0fd96123`, source hash `0d161bba2bcc6bdf0ad79392f5c4694b955342723e51f8ebd7fe03f7f387f45f`.
- 플랫폼·로직은 실제 Static Hermes 네이티브 O3 오브젝트다. JS 소스를 인터프리터에 넣은 결과나 디버그 빌드 결과로 설명할 수 없다.

## 1. 시작 지연의 대부분은 초기 스크립트 완료 이전에 발생한다

기존 시작 추적 12회/엔진의 평균:

| Rust main 이후 단계 | AOT | web |
|---|---:|---:|
| 초기 스크립트 완료 후 driver-start | 156.47ms | 113.02ms |
| 두 앱 프레임 대기 후 ready | 228.46ms | 183.44ms |
| 첫 고유 앱 버퍼 제시 | 234.40ms | 192.15ms |

driver-start 전에 이미 43.45ms 차이가 난다. driver-start→ready는 각각 71.99ms와 70.42ms로 비슷하다. 프레임 대기를 시작 지연의 주원인으로 볼 근거가 없다.

기존 release의 `platform.o`, `logic.o`, `libhermesvm.so`를 링크한 별도 C++ 프로그램을 컴파일했다. 실제 JS 소스 평가 없이 네이티브 유닛을 초기화한다. 첫 실행을 버리고 새 프로세스 12회씩 측정했으며, 메모리 조회와 출력은 시간 측정 구간 밖에 두었다.

| 분리한 AOT 작업 | 중앙값 |
|---|---:|
| Hermes 런타임 생성 | 2.01ms |
| 호스트 함수 등록 | 0.006ms |
| CSS·HTML·선택자 플랫폼 유닛 초기화 | 31.41ms |
| 앱·호환 로직 유닛 초기화 | 0.32ms |
| Solid 셸·앱 마운트 및 미러 DOM 생성 | 8.80ms |
| 최초 DOM 명령 JSON 생성 및 C++ 문자열 변환 | 0.28ms |

이 실험은 Servo와 창을 실행하지 않는다. 마지막 37,096바이트 명령을 실제 Servo DOM에 적용하지 않으며, DOM 질의가 필요하면 실패하도록 했다. 따라서 위 값은 전체 창 실행을 대체하지 않는 분리 진단이다. 단계 합계 약 42.8ms는 기존 지연 차이와 비슷한 규모지만, 이 합계를 기존 시작 지연에서 그대로 뺀 최적화 효과를 주장하지 않는다.

플랫폼 의존성도 각각 별도 네이티브 유닛으로 O3 컴파일하여 새 프로세스 12회씩 실행했다:

| 독립적으로 import한 라이브러리 | 초기화 중앙값 | 초기화 중 누적 JS 할당 |
|---|---:|---:|
| cssstyle | 25.21ms | 8,057,968바이트 |
| parse5 | 4.95ms | 2,196,792바이트 |
| css-select | 0.32ms | 111,576바이트 |

독립 유닛은 공유 의존성·코드 배치·메모리 페이지 접근이 달라서 비용을 정확히 더하거나 제거 효과로 환산할 수 없다. 그래도 가장 큰 초기화 비용이 cssstyle이라는 사실은 직접 확인된다.

`app/platform.mjs`는 세 라이브러리를 시작 시 모두 초기화한다. 번들 크기는 약 2.4MiB다. web 쪽의 앱 번들은 약 33KiB이며 CSSOM·HTML 파싱·선택자를 Servo의 기존 DOM에서 처리한다. cssstyle의 속성 정의, 파서 데이터, 객체·Map·함수 생성은 AOT로 컴파일해도 런타임에 수행된다. `Element.style` 객체 자체는 이미 지연 생성되므로, 모든 요소에서 이를 무조건 생성한다는 설명은 잘못이다. 문제는 플랫폼 라이브러리 전체의 선행 초기화다.

## 2. 메모리는 추가 힙뿐 아니라 실행 코드 페이지도 늘어난다

기존 패키지를 GNOME Wayland에서 순서를 교대한 네 쌍으로 실행했다. ready 1초 뒤 프로세스 트리의 `/proc/*/smaps`를 읽었다. 입력 주입이나 앱 변경은 하지 않았다.

| PSS 매핑 분류 | AOT 평균 | web 평균 | 차이 |
|---|---:|---:|---:|
| 익명 메모리·힙 | 52.69MiB | 36.88MiB | +15.81MiB |
| 실행 파일 매핑 | 83.96MiB | 75.72MiB | +8.24MiB |
| Hermes 라이브러리 | 4.37MiB | 0.38MiB | +4.00MiB |
| 장치·memfd | 3.73MiB | 3.06MiB | +0.67MiB |
| 기타 파일 | 16.33MiB | 16.29MiB | +0.04MiB |
| 합계 차이 | | | **+28.76MiB** |

실행 파일 차이 중 약 7.55MiB가 실행 가능한 코드 페이지, 약 0.61MiB가 읽기 전용 페이지다. AOT 코드와 관련 실행 경로를 사용하는 비용이 실제 상주 메모리로 나타난다. 실행 파일의 디스크 크기 전체를 RAM으로 계산한 값이 아니다. 익명 메모리 분류에는 JS 힙 외에도 allocator·스택·네이티브 자료구조 등이 포함되므로 15.81MiB 전체를 Hermes 객체로 단정하지 않는다. 장치·memfd 값은 프레임 버퍼 상태에 따라 변동하며 GPU 메모리 전체를 포괄하지 않는다.

이는 원래 40표본 측정의 +29.29MiB와 유사하지만, 원래 보고서를 대체하는 값은 아니다. 공유 페이지의 PSS는 동시에 실행 중인 다른 프로세스에도 영향을 받는다.

원래 ready 시점 Hermes 지표는 heapSize 12MiB, allocatedBytes 약 6.45MiB, young GC 4회, GC CPU 약 3ms였다. 12MiB는 추가 PSS 전체가 아니며 가상 주소·힙 용량과 실제 상주량을 같게 볼 수 없다. 별도 진단에서 강제 GC 후 allocatedBytes는 6,597,600→5,482,120바이트로 줄었지만 PSS는 거의 줄지 않았다. 코드 페이지와 유지되는 힙 용량도 있기 때문이다. 이 결과만으로 누수나 누수 부재를 판단하지 않는다.

## 3. 브리지와 DOM 표현이 추가된다

현재 경로는 다음 작업을 수행한다:

1. SpiderMonkey 어댑터에서 요청을 JSON으로 직렬화한다.
2. Rust 호스트가 telemetry 판별을 위해 JSON을 읽고, DOM 경로에서 다시 타입 검증·직렬화한다.
3. C++/JSI에서 문자열을 변환하고 Hermes가 요청 JSON을 파싱한다.
4. Hermes가 미러 DOM을 변경하고 명령 JSON을 생성한다.
5. Rust가 응답을 역직렬화·직렬화하고 SpiderMonkey가 다시 파싱하여 실제 Servo DOM에 적용한다.

별도 노드 래퍼, 속성·리스너 자료구조, 작업 큐가 실제 DOM과 함께 존재한다. `native/hermes.cpp`의 `host_call`은 매번 상태 보고 함수도 호출한다. 이는 이벤트·애니메이션 경로에서 줄일 수 있는 작업이다. 다만 현재 진단은 각 직렬화·동기 대기 비용을 따로 계측하지 않았으므로 수치 기여도를 단정하지 않는다. 시작 시 최초 명령 JSON 생성만은 위 표처럼 약 0.28ms로, 31ms 플랫폼 초기화보다 작았다.

## AOT에 기대한 이점이 바로 나타나지 않는 이유

AOT는 실행 중 소스 파싱·코드 생성 비용을 미리 치르게 할 수 있다. 하지만 JS의 동적 객체, GC, 모듈의 최상위 초기화, DOM·렌더링, 동기 통신 비용을 자동으로 제거하지 않는다. 네이티브 코드가 바이트코드보다 더 많은 메모리 페이지를 사용할 수도 있다.

SpiderMonkey도 처음부터 모든 코드를 고비용 최적화 JIT로 컴파일하는 구조가 아니다. 인터프리터와 단계별 최적화를 사용한다. 작은 UI의 첫 화면에서는 큰 JIT 비용을 상쇄할 만큼 AOT 절감분이 생기지 않을 수 있다. 실제 이 워크로드의 JIT 시간·코드 캐시는 아직 프로파일링하지 않았으므로 이를 0이라고 주장하지 않는다. [Mozilla의 SpiderMonkey 실행 단계 설명](https://firefox-source-docs.mozilla.org/js/how-we-optimize.html).

두 경로 모두 Servo의 창·폰트·스타일·레이아웃·그래픽 초기화가 필요하다. 현재 결과는 그 공통 비용 위에서 AOT 경로에만 무거운 호환 계층이 추가되는 구조로 설명된다.

## 개선 우선순위와 아직 확인하지 않은 것

1. cssstyle/CSS 파서의 시작 초기화를 줄인다. 정적 데이터의 미리 생성, 필요한 시점까지 유닛 초기화 지연, Servo CSSOM에 위임하는 방식을 각각 비교해야 한다. 첫 화면에서 해당 API를 쓰면 지연 초기화만으로는 비용이 사라지지 않는다. 호환성 기준을 줄이는 방식은 이번 분석에서 채택하지 않았다.
2. 중복 DOM·속성 저장과 JSON 왕복을 줄인다. 브리지 세부 단계에 타이밍·바이트 계측을 넣은 뒤, 비용이 큰 호출을 네이티브 바인딩으로 옮긴다.
3. Hermes가 Servo DOM에 직접 접근하는 경로를 검증하고 SpiderMonkey 의존성을 단계적으로 축소한다. 현재 Servo의 DOM/GC/바인딩은 SpiderMonkey와 결합되어 있으므로 엔진 제거는 별도 구현·컴파일·검증이 필요하다.
4. 각 변경을 기존 호환성·Wayland 입력 검사와 동일 벤치마크로 다시 측정한다. 작은 런타임 예제에서의 개선을 완성된 앱 성능으로 대체하지 않는다.

현재 확정할 수 있는 원인은 **큰 호환 라이브러리의 실행 시 초기화, 두 런타임과 DOM 표현의 공존, 추가 코드 페이지의 상주**다. cssstyle의 어느 내부 데이터·함수 생성이 시간을 가장 많이 쓰는지, 브리지의 세부 비용, 실제 JIT 시간, 최적화 후 개선 폭, 콜드 스타트 결과는 후속 검증 대상이다. 이번 작업에서 최적화 패치를 적용했다고 주장하지 않는다.

후속으로 지연 초기화 대안을 네이티브 컴파일하여 비교했다. 현재 첫 화면은 CSS 처리를 즉시 요구하므로 플랫폼 초기화 비용이 앱 마운트로 이동했고 전체 비용 절감은 확인되지 않았다. [지연 로딩 실험과 직접 CSS 바인딩의 검증 항목](lazy-loading-validation.md)을 참고한다.
