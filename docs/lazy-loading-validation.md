# 지연 로딩 검증 — 2026-10-19

이 문서는 당시 지연 로딩 대안만 검증한 기록이다. 이후 구현한 Servo CSSOM 바인딩과 SDK의 현재 상태는 [프레임워크 검증](framework-validation.md)을 참고한다.

CSS·HTML·선택자 라이브러리를 첫 사용 시 초기화하도록 바꾼 진단용 플랫폼을 실제 Static Hermes 네이티브 O3 코드로 컴파일했다. 기존 release의 앱·셸·미러 DOM 로직 오브젝트와 같은 Hermes 런타임에 링크했다. 애플리케이션 소스와 패키지는 변경하지 않았다.

## 실행 결과

첫 실행을 제외하고 기존 방식과 지연 방식을 번갈아 새 프로세스에서 각각 12회 실행했다. 모든 컴파일이 종료된 뒤 측정했다. 중앙값은 다음과 같다.

| 작업 | 기존 선행 초기화 | 첫 사용 시 초기화 |
|---|---:|---:|
| 플랫폼 유닛 초기화 | 31.12ms | 0.97ms |
| 앱·호환 로직 유닛 초기화 | 0.30ms | 5.57ms |
| Solid 셸·앱 마운트와 미러 DOM 생성 | 8.71ms | 34.03ms |
| 런타임 생성부터 최초 명령 생성까지 전체 | **42.77ms** | **43.32ms** |
| 최초 명령 생성 후 프로세스 PSS | 35.21MiB | 35.72MiB |
| 같은 시점의 Hermes 힙 용량 | 12MiB | 12MiB |
| 같은 시점의 Hermes allocatedBytes | 6,597,600 | 6,212,896 |

전체 시간은 각 프로세스에서 단계 시간을 합한 값의 중앙값이다. 단계별 중앙값의 합과는 다를 수 있다. PSS에는 실행 파일·라이브러리 페이지가 포함되며, 두 진단 실행 파일의 코드 배치와 공유 페이지 상태가 달라 작은 차이를 우열로 해석하지 않는다.

양쪽이 생성한 최초 DOM 명령은 37,096바이트였고, 워밍업을 포함한 모든 26회에서 JSON 내용이 같았다. 비용을 피하기 위해 화면 기능을 생략한 실험이 아니다. 유의미한 전체 시간·최종 메모리 절감은 확인되지 않았다.

## 왜 비용이 남는가

- `aot/browser-html.js`와 `aot/browser-selectors.js`는 로직 유닛 초기화 시 플랫폼 객체를 읽는다. 그래서 해당 라이브러리 초기화가 플랫폼 단계에서 로직 단계로 이동한다.
- `app/src/compatibility-app.tsx`의 첫 화면에는 크기·배경색·transform을 지정하는 `style` 객체가 있다. Solid가 화면을 마운트하면서 이를 설정하므로 `cssstyle`이 곧바로 필요해진다.
- 지연 방식은 네트워크에서 코드를 가져오거나 JS를 실행 중 컴파일하지 않는다. 번들 내부의 모듈 초기화 함수를 첫 접근 시 실행한다. Node 런타임은 사용하지 않는다.

사용하지 않는 기능을 끝까지 초기화하지 않는 앱에는 이 방식이 도움이 될 수 있다. 현재 시제품에서는 첫 화면이 해당 기능을 사용하므로 비용 발생 시점이 이동한다. 이번 실험으로 다른 앱의 지연 로딩 효과까지 부정하지 않는다.

## 해결할 작업의 경계

큰 비용을 줄일 구체적인 대상은 **Hermes 쪽 CSS 파서·CSSOM의 중복 구현**이다. 실제 Servo DOM에는 이미 CSSStyleDeclaration과 CSS 파싱 기능이 있다. 기존 scoped DOM query 경로에 인라인 스타일 접근을 연결하면, 앱 로직은 계속 Hermes AOT에서 실행하면서 CSS 의미 처리는 Servo에 맡길 수 있다. 현재 경로는 getComputedStyle·레이아웃·스크롤 질의를 이미 처리한다.

직접 바인딩을 구현할 때는 단순히 문자열을 넘기는 것만으로 끝내면 안 된다:

1. `style.cssText`, camelCase 속성, `setProperty`·`removeProperty`·우선순위·인덱스·동일 객체를 유지한다.
2. 스타일 변경 시 미러의 style 속성·Attr 동일성·MutationObserver 기록을 갱신한다. 실제 DOM에 같은 변경을 두 번 적용하지 않는다.
3. 미적용 DOM 명령을 먼저 반영하고, 분리된 노드·만료된 세션·재진입·네이티브 예외를 기존 규칙대로 처리한다.
4. CSS 파서 fallback이 같은 시작 경로에서 다시 초기화되지 않는지 확인한다. 단독 런타임 검사와 실제 Servo 검사의 실행 조건을 명시적으로 구분한다.
5. 고정 호환성 기준과 실제 Wayland 입력·애니메이션 검사를 통과시킨 뒤 전체 앱 시작 시간·PSS·입력 지연을 재측정한다. 동기 호출 증가가 애니메이션 경로를 악화시키지 않는지 확인한다.

이 바인딩은 아직 구현하거나 검증하지 않았다. 따라서 25ms가 그대로 절감된다거나 AOT가 web보다 빨라진다고 확정하지 않는다. 두 런타임과 미러 DOM의 나머지 비용도 별도로 남는다. 실효성이 확인되지 않은 지연 로딩 실험은 기존 앱에 적용하지 않았다.
